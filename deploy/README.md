# RouteTimer deployment

1. Set `ROUTETIMER_DB_PASSWORD` and `KEYCLOAK_AUTHORITY` (for example `https://auth.example.com/realms/routetimer`) in the deployment environment. `Auth__Mode` is set to `Keycloak` by the Compose file and must not be removed: the application refuses to start without an explicit authentication mode. Neither is a build argument any more — the image is built once and configured at run time.
2. Generate the Garmin token-encryption key with `openssl rand -base64 32` and store the output in the deployment secret named `ROUTETIMER_GARMIN_TOKEN_KEY`. Do not commit the value, put it in Compose YAML, paste it into an issue, or include it in a screenshot or log bundle. RouteTimer passes this key only to the API; the private Garmin adapter receives neither this key nor database credentials. The fixed key in `appsettings.Development.json` exists only so the app starts on a developer machine — it is published in this repository and must never be used in a deployment.
3. Treat the Garmin key as persistent data. Rotating or losing it makes the existing encrypted Garmin token bundle unreadable and requires the rider to reconnect Garmin. For planned rotation, disconnect Garmin first, replace the deployment secret, restart RouteTimer, and reconnect. Imported FIT evidence, parsed activities, and model history remain after disconnect.
4. Replace `ROUTETIMER_HOSTNAME` in `keycloak/routetimer-realm.json` and in `caddy/routetimer.caddy` (as `routetimer.example.com`) with the deployment's real hostname, then import the realm file into the existing Keycloak instance. Assign the realm `rider` role to the rider account. Neither file reads its placeholder from this Compose project's or the shared ingress's own environment — both are plain text substituted by hand here (or by an automated deployment script performing the same substitution).
5. Before the first deploy, a backup baseline isn't meaningful yet — there is no database. From the second deploy onward, run `deploy/backup.sh deploy/docker-compose.yml` first. A schema migration has no reverse path; the backup is how you get back to a known state if a deploy goes wrong.
6. Set `ROUTETIMER_IMAGE_TAG` to the image tag you intend to run (a commit SHA or version tag published by CI; see the repository's GitHub Actions runs), then start with `docker compose -f deploy/docker-compose.yml up -d`. The app, adapter, and database publish no host ports; only the app joins `mcp-public`. RouteTimer reaches the adapter at `http://routetimer-garmin-adapter:8081` on the internal `routetimer-private` network and waits for its health check before starting. Only the adapter also joins the non-internal `garmin-egress` bridge so it can initiate Garmin HTTPS requests; RouteTimer and PostgreSQL do not join that egress network.
7. Copy `caddy/routetimer.caddy` into the shared ingress drop-in directory, validate Caddy, then reload it — never restart the shared ingress just for this. Do not add a Caddy route for the Garmin adapter.
8. Confirm `curl -f https://<hostname>/health/ready` returns `200`.
9. Run the opt-in real-account procedure in [`docs/garmin-smoke-test.md`](../docs/garmin-smoke-test.md) before releasing this unofficial integration or after upgrading its pinned Garmin dependency. It must remain outside CI.
10. Treat `garmin-adapter/requirements.lock` and the Python base-image digest as reviewed release inputs. After intentionally changing a dependency pin in `pyproject.toml`, install `pip-tools==7.5.1` in the adapter's local virtual environment and regenerate the lock with `.venv/bin/pip-compile pyproject.toml --output-file requirements.lock --generate-hashes --resolver backtracking --strip-extras --all-build-deps --allow-unsafe`; review the resolved versions and hashes, then rerun Python checks and the adapter Docker build. Refresh the `python:3.12-slim` digest deliberately when adopting an upstream base update. CI publishes the resulting image; this step prepares that change, it does not deploy it.
11. **Optional — "Open in PaceTracker".** Off unless deliberately enabled, and it adds no inbound exposure: RouteTimer only makes an outbound HTTPS call to the relay, so do not add a Compose `ports:` entry or a Caddy route for it. Deploy the RoutePacer relay first, then set `ROUTEPACER_HANDOFF_ENABLED`, `ROUTEPACER_RELAY_UPLOAD_KEY`, and `ROUTEPACER_SIGNING_PRIVATE_KEY_PEM` in an untracked, `chmod 600` `deploy/.env`. With the feature enabled and either secret empty, RouteTimer refuses to start — that is deliberate, and it is how a missing `.env` surfaces. Note the privacy consequence before enabling: relay content is plaintext for up to ten minutes. Full procedure, key generation, smoke test, and rollback order in [`docs/routepacer-handoff.md`](../docs/routepacer-handoff.md).

## Rollback

Redeploy the previous `ROUTETIMER_IMAGE_TAG` and run `docker compose -f deploy/docker-compose.yml up -d` again. If the previous deploy applied a database migration, an older image is not guaranteed to work against the newer schema — restore the backup taken in step 5 first.

To roll back the PaceTracker handoff specifically, disable RouteTimer first: set `ROUTEPACER_HANDOFF_ENABLED=false` and restart, which removes the action while leaving GPX download, visualization, and Garmin untouched. Let outstanding relay payloads expire (ten minutes at most), then disable the RoutePacer intake if that is also intended.
